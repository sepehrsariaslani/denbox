## Network boundary

The Retrofit base URL is read from a downloaded configuration file, rather than being fixed in the app. Static code shows the APK fetching that file over plain HTTP; the manifest also permits cleartext traffic. For the Mac build, the same config file was fetched over HTTPS (without an API key) and returned the current host `ninwinios.info`. Simba now calls that host through HTTPS as `ninwinios.info/api`. Its `first/{key}` response contains metadata collections and an empty `channels` list, so movie and series catalog rows continue to come from the separate HTTPS feeds.

## Direct API implementation from `denflow`

The Mac app uses the separate API setup present in the user-provided `denflow` source, rather than Frappe routes or the APK's undocumented service. The source defines movie and series catalog feeds on `rubyxpin.info`, a search API on `gitcss.info`, and movie/series detail routes on `gitcss.info`. Their credentials are read from that local source and stored in macOS Keychain; no credential values are embedded in the app or this document.

The catalog feeds, search endpoint, and a movie detail request were contacted over HTTPS. The feeds returned 30 rows each and the detail response included source metadata. Playback URLs are HTTP-only: a range request to a current source redirected from `dl175m.info` to `gooyaserver.com` and returned HTTP 206; upgrading that source to HTTPS failed certificate validation. For this personal build, ATS is now disabled globally so AVKit can follow plain-HTTP sources and redirects from any host. API calls in the app still use HTTPS. This broad setting reduces security for every network connection made by the app. Simba caches catalog records and its local My List in SQLite under the user's Application Support directory. It does not bypass authentication, subscriptions, DRM, or player restrictions.

The app does not call Frappe endpoints. Its source contains only the API route shapes and Keychain lookups, not the user's API keys.

## Public Filimo and HexDL metadata pages (REA)

- New REA controlled-browser samples confirmed the public page exposes more fields than the initial search summaries. Filimo detail pages show Persian plot and episode summaries/durations, seasons, genres, IMDb score, year/country, and age labels. HexDL detail pages show Persian plot, genres, country/year, content rating, season/episode rows, cast/producer credits, and release labels such as subtitle/quality. Denbox saves the public JSON search result immediately for fast catalog enrichment; opening a title then captures visible title-page facts and merges them, while the **Search public pages** detail action forces a fresh capture. This keeps catalog-wide API lookups independent of slower page rendering.
- Denbox saves Persian synopsis, original title, poster, year/country, genres, content rating, IMDb/site rating, runtime, director, season/episode counts, cast/crew, public labels, visible episode details and any shown summaries, and source page URL in the existing SQLite JSON table. Old records remain decodable and an enrichment-version marker queues them for refresh. IMDb ratings/genres/years remain primary when present; TVmaze images and character names stay associated with IMDb cast. Persian descriptions remain preferred over English summaries. If a JSON route is unavailable, Denbox falls back to the visible search in non-persistent WebKit. Successful complete matches refresh after 30 days; failed/incomplete searches cool down for 24 hours; detail and Settings actions can force a new lookup.
- The importer does not sign in or read player, stream, or download links. Simba's existing API remains the only media playback/download source. Static APK inspection found Simba API classes but no HexDL-named integration; HexDL is therefore handled as a separate public metadata site, not as an APK endpoint.
- REA evidence, all observed in controlled browser scenarios on 2026-10-16: Filimo public JSON `ev_bf45b8aa758ba8674080fbd69953bb4d593f643f59719fae180f52819ccfeee8` and category/country object shape `ev_3af0951feb44ce05fe5bbda10384eabd26ecb554f677233e31e571c8bdae63f2`; HexDL public search JSON `ev_50d9c844fc7962bec558f99bfc58cfa14071be7b2017ebc9b5ca848418dc564a`; Filimo visible detail page `ev_d7b5d359b7f8860ceb81bde2f7dfdc2cb31885aefcedc99196aa0566401a132`; HexDL visible detail page `ev_0de69f8a21d324351f26c448ba32e74e6fc447a3c75eda7c338b6406f6dfe99f`. ## IINA macOS player analysis (REA)

- Reference executable: `/Applications/IINA.app/Contents/MacOS/IINA`.

- Static analysis found IINA's player built on libmpv with an OpenGL renderer. Its `MPVController.mpvInit` sets up libmpv, configuration/input paths, watch-later, subtitle, hardware-decode, and OSD options.

- IINA online subtitle search routes through `menuFindOnlineSub` and has concrete `ShooterSubtitle`, `OpenSubSubtitle`, and `AssrtSubtitle` download implementations (`ev_b48552e1da2889a0c998e3cb094f397f830ca1ae5154c2bed4390e8549b70797`; search UI path `ev_57542b0cd8b2633eb34e72eb443d0c5805e6a326ddc39ca274c642d718dd50f0`). Follow-up Ghidra inspection found that IINA selects Shooter, OpenSubtitles, or Assrt according to a saved provider preference, hashes local files for Shooter, and uses OpenSubtitles' legacy XML-RPC client for name/IMDb searches (`ev_19df8d209e995e8ca053e212ad1e65df5cfea06a829adad5b5a625c3ea8cd000`; search results `ev_994351f270c2f95ba08c173868b988f21ef8d61901e1c21ea4c6c9ae5e05c6d0`, `ev_9cac01f2e439926aeafbfa03d78bbdbdc9ba40f69ddf679186695cd1dba543ab`).
